一、现场诊断方案（无需改动代码，立刻定位卡死点）
在程序卡死不动的瞬间，通过以下命令抓取第一现场状态：

1. 抓取 Go 运行时所有 Goroutine 堆栈（最直接有效的手段）
Go 语言原生支持通过 SIGQUIT 信号导出当前所有协程的调用栈和阻塞状态：

bash
# 1. 查找 reality-checker 的进程 PID
PID=$(pidof reality-checker)
# 2. 发送 SIGQUIT 信号触发堆栈打印并生成 core dump（不会损坏数据）
kill -QUIT $PID 2>&1 | tee /tmp/goroutine_dump.log
排查重点： 在输出的 /tmp/goroutine_dump.log 中搜索状态为 [select], [chan receive], [chan send], [semacquire] 或 [IO wait] 的协程，直接能看到卡死在具体哪一个文件的哪一行代码（例如 scanner.go、store.go 或 pipeline.go）。

2. 排查 NanoPi 嵌入式 Linux 系统级资源枯竭
threads = 2000 在 ARM 嵌入式设备上属于极高并发，极易触发 Linux 内核网络与文件句柄瓶颈：

bash
# A. 检查连接跟踪表（nf_conntrack）是否被打满（打满后内核会丢弃所有包导致假死）
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max
dmesg | grep -i "nf_conntrack: table full"
# B. 检查当前进程打开的文件句柄数与最大限制
ls /proc/$PID/fd | wc -l
cat /proc/$PID/limits | grep "Max open files"
# C. 检查 TCP 连接堆积状态 (SYN_SENT, TIME_WAIT)
ss -s
netstat -n | awk '/^tcp/ {++S[$NF]} END {for(a in S) print a, S[a]}'
# D. 检查内存与 SD卡/eMMC I/O 阻塞
free -m
vmstat 1 5
dmesg | grep -i "oom"
